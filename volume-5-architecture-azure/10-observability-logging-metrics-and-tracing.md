# Observability: Logging, Metrics and Distributed Tracing

## Overview

One of the biggest differences between junior and senior engineers is what they think about after deploying an application.

Junior developers ask:

> "Does it work?"

Senior engineers ask:

> "How will we know when it stops working?"

Observability is the ability to understand the internal state of a system by observing its outputs.

The three pillars of observability are:

- Logs
- Metrics
- Traces

Together they help engineers detect, diagnose and resolve production issues quickly.

---

# 1. What is Observability?

## Interview Answer

Observability is the ability to understand what is happening inside a system without directly inspecting its internal state.

It answers questions like:

- Why is the API slow?
- Which service is failing?
- Where did the request spend most of its time?
- Why did only some users experience an error?

Observability combines logs, metrics and traces to provide a complete picture.

---

# 2. Logs

## Interview Answer

Logs are timestamped records describing events that occurred inside the application.

Examples:

- User logged in.
- Order created.
- Database timeout.
- Exception thrown.

Example:

```csharp
_logger.LogInformation(
    "Order {OrderId} created for customer {CustomerId}",
    order.Id,
    order.CustomerId);
```

---

## Structured Logging

Prefer structured logging instead of string concatenation.

Bad:

```csharp
_logger.LogInformation(
    "User " + id + " logged in");
```

Good:

```csharp
_logger.LogInformation(
    "User {UserId} logged in",
    id);
```

Structured logs allow filtering and querying by properties.

---

# 3. Log Levels

ASP.NET Core defines several log levels.

| Level | Purpose |
|--------|----------|
| Trace | Extremely detailed debugging |
| Debug | Development diagnostics |
| Information | Normal business events |
| Warning | Unexpected but recoverable |
| Error | Operation failed |
| Critical | Application may stop working |

---

## Interview Question

### Should exceptions always be logged as Critical?

## Answer

No.

Most application exceptions are logged as Error.

Critical is reserved for failures that threaten the application's ability to continue running.

---

# 4. Metrics

## Interview Answer

Metrics are numerical measurements collected over time.

Examples:

- Requests per second
- CPU usage
- Memory usage
- Average response time
- Error rate

Unlike logs, metrics are aggregated and ideal for dashboards and alerts.

---

# Common Metrics

Application:

- Request duration
- Active users
- Queue length
- Failed requests

Infrastructure:

- CPU
- RAM
- Disk
- Network

Database:

- Query duration
- Deadlocks
- Connections
- Cache hit ratio

---

# 5. Tracing

## Interview Answer

Tracing follows a single request as it travels through multiple services.

Example:

```
Client

↓

API Gateway

↓

Order Service

↓

Payment Service

↓

Inventory Service

↓

SQL
```

Instead of isolated logs, tracing shows the complete request journey.

---

# 6. Trace ID

Every request receives a unique identifier.

Example:

```
TraceId

↓

9c8f4d...
```

Every service logs the same TraceId.

This allows engineers to reconstruct the entire request flow.

---

# 7. Correlation ID vs Trace ID

## Correlation ID

Usually identifies a business request across services.

Example:

```
Order #12345
```

---

## Trace ID

Generated by the tracing system.

Represents one distributed request.

Modern systems often use Trace IDs automatically through OpenTelemetry.

---

# 8. OpenTelemetry

## Interview Answer

OpenTelemetry is the industry standard for collecting:

- Logs
- Metrics
- Traces

It is vendor-neutral.

Collected telemetry can be exported to:

- Azure Monitor
- Jaeger
- Zipkin
- Grafana Tempo
- Datadog
- New Relic

This prevents vendor lock-in.

---

# 9. Serilog

Serilog is one of the most popular structured logging libraries in .NET.

Example:

```csharp
Log.Information(
    "Payment {PaymentId} completed",
    paymentId);
```

Serilog supports many sinks:

- Console
- File
- Seq
- Elasticsearch
- Azure Monitor

# 10. Dashboards

Metrics become useful when visualized.

Typical dashboards include:

```
Requests/sec

Average latency

95th percentile latency

Error rate

CPU

Memory

Queue length
```

Dashboards help detect trends before users report problems.

---

# 11. Alerts

Monitoring without alerts is incomplete.

Examples:

Alert if:

- Error rate > 5%
- CPU > 90%
- Queue length > 10,000
- Response time > 2 seconds

Alerts should be actionable.

Avoid generating alerts for every minor issue.

---

# 12. Common Interview Questions

### Why are logs alone insufficient?

## Answer

Logs explain individual events but don't provide trends or end-to-end request visibility.

Metrics reveal trends.

Traces reveal request flow.

All three are needed.

---

### Should every request be logged?

Not necessarily.

High-volume systems often sample requests or reduce log verbosity to control storage costs.

---

### Why is structured logging preferred?

Because it allows searching and filtering by fields instead of parsing free-form text.

---

### Can tracing work without logs?

Yes.

Tracing shows request flow.

Logs provide detailed context.

Together they are far more valuable.

---

# Trade-offs

| Tool | Best For | Limitation |
|------|----------|------------|
| Logs | Detailed diagnostics | High storage cost |
| Metrics | Trends and alerting | Limited context |
| Traces | Distributed request flow | More complex setup |

---

# Staff Engineer Insight

One of the biggest production mistakes is logging too much or too little.

Examples:

Bad:

- Logging passwords.
- Logging JWT tokens.
- Logging entire request bodies containing personal data.

Also bad:

- Logging only "Something went wrong."

Good logs should answer:

- What happened?
- Which user?
- Which request?
- Which service?
- Which correlation/trace ID?
- Can I reproduce the problem?

Another common mistake is relying only on application logs.

Production troubleshooting often requires correlating application logs, infrastructure metrics and distributed traces.

---

# Summary

- Observability helps understand system behavior in production.
- Logs record individual events.
- Metrics measure trends over time.
- Traces follow requests across services.
- Use structured logging whenever possible.
- Assign a Trace ID to every request.
- OpenTelemetry is the standard for observability.
- Dashboards and alerts are essential for operating distributed systems.
- Good observability reduces Mean Time To Resolution (MTTR).
